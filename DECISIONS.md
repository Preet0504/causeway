# Decisions log

A running, day-grouped record of design decisions made on the `causeway-mini` branch, with brief rationale. Forward-only: it starts from the day this file was created and doesn't reconstruct earlier history.

## 2026-09-09

- **Split `bugCap` into `scanCommitLimit` and `bugTarget`.** The single `bugCap` field was asked during `/inspect_repo` (before anything was known to be a bug) but named as if it capped bugs found, which is a real terminology bug, not just a naming preference. `scanCommitLimit` (renamed from `bugCap`) now caps how many commits get scanned in detail; its question in `/inspect_repo` deliberately never mentions "bugs". A new `bugTarget`, asked in `/classify_bugs` once the user knows how many commits were enriched, caps how many accepted results they want.
- **`/classify_bugs` processes commit batches sequentially, newest first, and stops once `bugTarget` is reached**, instead of fanning out every batch of subagents in parallel. Trades the earlier parallel design's speed for fewer subagent calls when the target is smaller than the scanned set. Accepted tradeoff: which commits actually get examined depends on batch order (newest first) rather than which would score best, since there's no way to know that without examining them.
- **Added this decisions log**, `DECISIONS.md` at the repo root, day-grouped entries with brief rationale, forward-only (no retroactive reconstruction of earlier sessions).

## 2026-09-11

- **Removed the early-exit optimization from `InspectRepo`'s window filter.** The user's professor identified a real correctness bug: stopping the walk as soon as one commit older than the cutoff was seen assumed commit timestamps are monotonic along the traversal, which is false for real Git histories (clock skew, rebases, backdated commits, merges of independently-developed branches can all produce a parent with a later timestamp than its own child). The fix visits every commit reachable from HEAD and filters each individually, no shortcut. Traded back some of the walk-speed win from the 2026-09-05 early-exit optimization in exchange for correctness, since a fast wrong answer isn't useful. Extracted the filtering logic into a standalone `findCommitsInWindow` function so it's unit-testable outside the CLI's clone/write machinery.
- **Added a regression test with deliberately skewed commit timestamps** (`InspectRepoWindowSpec`), building a tiny real Git repo by hand where a middle commit is backdated to before its own parent, and asserting the parent (genuinely recent, but "behind" the backdated commit in the walk) is still found. Verified the test actually catches the bug by temporarily reintroducing the old early-exit logic and confirming the test fails there, then confirming it passes again with the fix restored, rather than trusting a passing test without having seen it fail first.
- **Added MUnit (1.1.1) as the project's first test dependency.** No test framework existed yet; MUnit is lightweight and standard for Scala 3, and there was no reason to build anything custom for this.
- **`InspectRepo` now fetches from the remote and pins an explicit repository snapshot on every run, instead of silently reusing whatever a local clone happened to contain.** The professor's follow-up feedback: the repo URL alone does not define repository state, a reused clone with no fetch can produce different results from identical arguments depending only on when it happens to run, and the file's own doc comment claiming determinism was false without something recording what state was actually examined. The evidence file now carries a `repoSnapshot` (`defaultBranch`, `remoteHeadSha`, `retrievedAt`, `usedLocalHeadFallback`), fetched forward through `EnrichCommits` and `/classify_bugs`'s final JSON too, so the whole pipeline's output ties back to one recorded remote state. `findCommitsInWindow` now takes that pinned SHA as an explicit parameter rather than resolving `HEAD` internally, so later operations can't silently drift onto whatever HEAD happens to be at call time.
- **Rejected `refs/remotes/origin/HEAD` as the source of the pinned SHA, uses `repository.getBranch()` (the locally checked-out branch name) plus `refs/remotes/origin/<that branch>` instead.** Tried the symbolic-ref approach first; JGit's `CloneCommand` does not reliably set up `refs/remotes/origin/HEAD` the way plain `git clone` does, so it fell back to local `HEAD`, which is itself never updated by a plain fetch, silently reproducing the exact staleness bug being fixed. Caught this by cross-checking the resolved SHA against GitHub's REST API directly rather than trusting a plausible-looking result.
- **Added a regression test for the fetch-and-pin fix** (`InspectRepoSnapshotSpec`), after being asked directly whether one existed and having to say no, the fetch/pin fix had only been checked by hand against a real GitHub repo. The test uses a local repo as a stand-in remote (no network dependency, so it runs the same everywhere), clones it, pushes a new commit to the stand-in remote, fetches, and asserts `resolveRemoteHead` returns the new commit rather than the one seen at the original clone. Verified it actually catches the bug the same way as the other regression test: temporarily reintroduced the rejected `origin/HEAD` approach, confirmed the test failed, restored the fix, confirmed it passed again.
- **Replaced auto-detection of remote and branch entirely with explicit user choice, discussed after asking "is it possible the selected remote isn't origin" surfaced the fork scenario (a repo's `origin` could be a fork, `upstream` the actual project being studied).** Rather than validating an assumed `origin` against expectations and failing on mismatch, the user proposed listing what's actually there and letting a person pick. `InspectRepo` now runs as four explicit modes (`list-remotes`, `list-branches`, `count`, `write`) instead of one auto-detecting pass. `resolveRemoteHead` and its test (`InspectRepoSnapshotSpec`) were removed, replaced by `listConfiguredRemotes` (tested by `InspectRepoRemotesSpec`, a fork-shaped clone with both `origin` and `upstream` configured, confirming both are surfaced rather than only `origin`) and a GitHub REST API branch listing (`list-branches`) that reports every branch's current SHA directly, so `count`/`write` trust an explicitly chosen SHA rather than resolving anything themselves. The `repoSnapshot` schema changed from `{defaultBranch, remoteHeadSha, retrievedAt, usedLocalHeadFallback}` to `{remoteName, branch, remoteHeadSha, retrievedAt}` to reflect a chosen value rather than a detected one.
- **Branch choice is asked as a plain-text question, not multiple-choice**, even though remote choice uses multiple-choice when there's more than one option. A repo can have many branches (JSON-java has 19), too many for the project's established 2-4-option multiple-choice pattern; the default branch is suggested but the user can type any other name.
- **Built a unified `causeway` CLI, replacing `sbt runMain` as how the chat commands invoke the Scala tools**, per the professor's suggestion that a packaged CLI is a cleaner agent-to-software contract than a build tool's invocation surface, especially as the number of Scala files grows. Discovered along the way that sbt 2's virtual file system, which blocked packaging a plain jar a few days earlier, only virtualizes the *packaged* output: `Compile/dependencyClasspath` returns real, stable paths in the Coursier cache, and compiled `.class` files exist as plain files under `target/out/.../classes`. A classpath doesn't require everything bundled into one jar, so a single `Causeway` main object (dispatching on a subcommand argument to `InspectRepo.run`/`EnrichCommits.run`, both renamed from `main`) plus `tools/causeway`, a launcher that caches that classpath and only re-invokes sbt when a source file or `build.sbt` is newer than the cache, gets the same practical benefit without needing to solve the jar problem at all. Confirmed live: cached invocations run in under a second with zero sbt involvement, versus sbt's several-second build-server round trip every time.
- **The launcher writes Windows-style paths (via `cygpath -w`), not Git Bash's `/c/Users/...` form.** First attempt used `$HOME`-derived MSYS paths directly and failed with `NoClassDefFoundError: scala/runtime/Nothing$`, since `java.exe` is a native Windows binary and Git Bash only translates path-shaped arguments passed literally on a command line, not paths embedded inside a file's contents (which is what a `java @argfile` classpath file is). Caught and fixed by inspecting the generated classpath file directly rather than assuming the failure meant a missing dependency.
- **Added a SQLite repository catalog (`workspace/causeway.db`) as an additive `store` subcommand**, per the professor's suggestion to persist repositories, snapshots, commits, issues, pull requests, issue-commit relations, test observations, bug classifications, materialized revisions, and build runs, each preserving its source/run identifier, with repeated operations upserting rather than duplicating. Kept explicitly additive alongside the existing JSON files rather than replacing them: `/inspect_commits` and `/classify_bugs` each consume the previous stage's JSON file directly and in full, and the JSON files remain the pipeline's actual interchange format. `store` detects which of the three JSON shapes (evidence, enriched, classified) it was given by field presence and upserts accordingly.
- **One table per pipeline stage (`inspect_repo_runs`, `inspect_commits_runs`, `classify_bugs_runs`) instead of one shared `runs` table with a stage/type column.** Matches the professor's own per-concept table style already implied by naming separate tables like `test_observations`, `materialized_revisions`, and `build_runs` rather than one generic table. Also gives downstream foreign keys a precise type: a `bug_classification` always points at a `classify_bugs_run`, never a generically-typed "run" that could be any stage.
- **A single `run_id` (UUID, already minted by `/inspect_repo` and already carried through the JSON files) is shared across all three stage tables of one mining pass**, rather than each stage minting its own. Raised directly by the user: "what if someone runs everything on the same repo but different window and stuff." Each stage table still has its own surrogate autoincrement `id` (used for foreign keys), `run_id` is just a `UNIQUE` column per table, not a cross-table primary key, so the three stage tables don't collide on it.
- **Added `run_commits`, a many-to-many join table between `inspect_repo_runs` and `commits`, instead of a plain column on `commits` recording which run found it.** The same commit can be legitimately rediscovered by a second run with a different window against the same repository (the exact scenario above); a bare column would have the second run's write silently overwrite the first run's membership record. Proven with a regression test (`StoreSpec`, "two different runs against the same repo, different windows") that stores two runs sharing one commit and asserts both runs' `run_commits` rows survive.
- **Author/committer fields on `commits` are upserted with `COALESCE(excluded.col, col)`, not overwritten outright**, because an enriched-file store happens after an evidence-file store for the same commits, and `EnrichCommits` strips author/committer data from its output (an earlier session decision, "these things are useless to me"). Without `COALESCE`, storing the enriched file after the evidence file would null out data the evidence file had already recorded.
- **Fixed a schema-loading bug where the entire `repositories` table definition was silently never created.** `applySchema` originally split `schema.sql` on `;` and filtered out chunks whose *trimmed text started with* `--`; because the file opens with a multi-line comment block directly followed by `CREATE TABLE repositories` with no blank statement between them, both ended up in the same split chunk, and the whole chunk (comment and the `CREATE TABLE` it preceded) got discarded, surfacing later as `no such table: repositories`. Fixed by stripping `--` comment lines individually, line by line, before splitting on `;`, rather than filtering whole semicolon-delimited chunks after the fact.
- **Live-verified `store` against a real evidence file, a real enriched file (from `stleary/JSON-java`), and a hand-built classified file**, reading the resulting `workspace/causeway.db` directly (via `py -c` and the `sqlite3` module, no `sqlite3` CLI available) rather than trusting "no exception thrown." Confirmed idempotency by storing the same evidence file twice and checking row counts stayed flat, and confirmed the PR/issue linking and the author/committer `COALESCE` preservation by inspecting the enriched-store's resulting rows directly.
- **Added `StoreSpec`, proving the run-scoped upsert design with a temp SQLite file per test**: one test stores the same evidence run twice and asserts no duplicate rows anywhere; the other stores two different runs (different `runId`, different window, one shared commit) against the same repository and asserts the repository row is reused, the two runs stay distinct, and `run_commits` correctly reflects both runs' membership for the shared commit. Verified these actually catch a real regression, not just exercise happy-path code, by temporarily removing the `commits` table's `ON CONFLICT` upsert clause, confirming both tests failed with a primary-key constraint violation, then restoring the fix and confirming the full suite (4 tests) passed again.
- **`Store.run` refactored to delegate to a new `private[mini] def storeInto(conn, json, filePath): String`** that takes an already-open `Connection` and returns the detected kind, instead of inlining schema-apply-and-dispatch directly inside `run`'s fixed-database-path, `sys.exit`-on-failure connection-management block. Pure extraction, no behavior change, done specifically so `StoreSpec` could point it at a disposable temp-file database instead of the real `workspace/causeway.db`.
